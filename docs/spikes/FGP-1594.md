# FGP-1594: integrated dedupe spike

[FGP-1594](https://eaflood.atlassian.net/browse/FGP-1594) is implemented as a
disposable change to the real applications, on backend branch `fgp-1594-spike`
and frontend branch `spike/fgp-1594-dedupe`. The earlier standalone HTML/model
experiment was reverted. These changes are for learning, not a production merge.

## What is connected

1. The real workflow contains `pages.case-list.tabs.duplicates.page-type`.
   `test/fixtures/dedupe-page.json` shows the exact config used by the seed and
   tests. Workflow publication/storage validates the new configuration and scope.
2. `/case-list-pages` discovers configured tabs for accessible workflows. The
   existing frontend `/cases` page links to them. The spike selects the newest
   active config version across majors for the list, using the existing config
   version and workflow repositories. Cases are not repinned by this read.
3. Backend routes are registered by the existing cases plugin. Their use cases
   enforce workflow roles, use the existing assignee lookup, and build the view
   model from the configured expressions. The frontend page-type registry selects
   a Nunjucks template and renders the backend's components and choices.
4. The repository groups real stored case documents in MongoDB, including scoped
   excluded cases, then applies the summary threshold. SHA-256 keys and owner
   hydration happen in JS after grouping. Details stay readable when the group
   drops below two active members.
5. One frontend form posts the owner and every enabled label. The frontend calls
   the backend PUT route. The backend validates before writing, hydrates real
   `Case` objects and calls `Case.setLabel`. A Mongo transaction stores changed
   labels, `TimelineEvent` entries, group ownership and the success audit outbox
   entry together. The frontend's existing timeline partial renders label changes.
6. `CaseDocument` and repository hydration preserve labels through ordinary case
   reads and saves. The new index migration creates unique group identity and a
   scope index on cases. No production route depends on a parallel prototype model.

Routes:

| Method | Backend path                                           |
| ------ | ------------------------------------------------------ |
| GET    | `/case-list-pages`                                     |
| GET    | `/case-types/:caseType/pages/:pageKey`                 |
| GET    | `/case-types/:caseType/pages/:pageKey/groups/:keyHash` |
| PUT    | `/case-types/:caseType/pages/:pageKey/groups/:keyHash` |

Frontend summary/group paths start at `/types/:caseType/pages/:pageKey`; the
group route supports GET and POST. POST redirects to the summary after success,
or re-renders the form with its choices and a validation error after refusal.

## Reproduce the integration evidence

Install locked dependencies with `npm ci` in each checkout. Use Node 24 meeting
the dependencies' engine requirements and a local Mongo replica set. From the
backend checkout:

```sh
# Full frontend templates/form -> backend HTTP -> real repositories -> Mongo.
# Set this to your frontend spike checkout.
FGP1594_FRONTEND=/path/to/fg-cw-frontend node scripts/verify-dedupe-spike.js

# Backend application route tests, including transaction rollback.
npx vitest run --configLoader native --config test/dedupe.vitest.config.js
```

Both commands default to local Mongo at `127.0.0.1:27017` with direct connection.
Override `SPIKE_MONGO_URI` for another local replica set. Each creates a uniquely
named `fgp1594-spike-tests-*` or `fgp1594-spike-e2e-*` database and removes it at
exit. They do not use the application database. Neither starts background queue
consumers. The cross-app command briefly listens on an ephemeral loopback port.

The cross-app check imports the existing frontend cases plugin and templates,
finds the configured tab on the existing case list, opens its summary/group,
submits form values, checks Mongo labels/timelines/owner, and reloads HTML to
verify persisted selections. It uses real frontend repository HTTP calls.
Only session/Entra authentication is substituted with the seeded user; this is
not an end-to-end login test or a browser/accessibility assessment.

## Try the actual applications

Use the usual local Mongo, Floci and Entra services for these repositories. Do
not start another Compose backend container on the same port as the worktree
process. The seed creates only synthetic data in a new scratch database and
refuses an existing non-empty database:

The seed command runs application migrations before adding the spike data. This
order matters: the initial migration drops/recreates collections, so seeding
before the first application startup would lose the cases and tab configuration.

```sh
# Backend checkout: set up its usual .env first.
MONGO_URI='mongodb://127.0.0.1:27017/?directConnection=true' \
MONGO_DATABASE=fgp1594-spike \
node --env-file=.env scripts/seed-dedupe-spike.js

# Backend: retain your usual local AWS/Entra env configuration.
MONGO_URI='mongodb://127.0.0.1:27017/?directConnection=true' \
MONGO_DATABASE=fgp1594-spike npm run dev

# Frontend checkout: set up its usual .env and run against the backend above.
FG_CW_BACKEND=http://localhost:3101 npm run dev
```

Use host-reachable AWS/Entra URLs in the backend `.env` when running outside
Compose; `.env.example` contains some container hostnames. Open
`http://localhost:3100/cases`, sign in with the bundled **Test ReaderWriter** user
and choose **Clean the list**. The seed uses that stub user's identity and the
existing FRPS workflow fixture with no grant-specific role restrictions.

The three seeded SBI groups have two active applications each. SBI 244666513
also has a rejected application. Try assigning an owner, completing labels,
saving twice, then reopening the group. Excluded selects are disabled; a reference
to a subsequently excluded case is preserved as a historical selection.

To exercise arrival or withdrawal, change documents in this scratch database
using a local Mongo client; the next request recalculates membership and status.
These are deliberately not dedupe actions. The Mongo integration tests include
repeatable versions of those changes.

## Evidence and limits

Verified on 12 November 2026:

- 291 backend model/schema/repository/registration checks pass, including the new
  evaluator tests and existing case/timeline/workflow regression tests.
- Eight Mongo route tests cover tab discovery, counts, config-only regrouping and
  scope changes, completion, arrival, persistent ownership, historical targets,
  invalid saves, exclusions, label clears, role checks and forced rollback.
- 18 frontend route/use-case/template/registration checks cover rendered links,
  controls, historical selections, read-only access, validation errors and save.
- Cross-repository HTTP/form check passes against MongoDB, including the existing
  case timeline API and rendered frontend timeline after a label save.

The backend's existing ESLint exception globs do not match hidden `.t3` checkout
paths. Changed files were linted with the same rules and absolute exception globs
in a temporary invocation; no rules were disabled for that workaround. Frontend
changed-file lint uses its normal config. Neither lockfile was changed.

## Findings and follow-up ticket drafts

1. **Complete workflow page-type support and config lifecycle.** Decide the list
   version policy across majors; test publication/cache/config changes; add a
   payload schema to catch misspelled grant payload paths during publication.
   The spike validates structural paths/functions but cannot prove a field
   exists in an arbitrary grant payload. Group key changes can orphan ownership
   and leave labels attached under the old interpretation; define migration or
   identity fingerprinting before allowing edits in production.
2. **Make generic labels concurrency-safe.** Add per-namespace revisions including
   clears/tombstones; optimistic group/label versions and 409 responses; protect
   labels and timelines from concurrent ordinary case saves. The spike preserves
   data on sequential reads/saves, but deliberately uses last-write-wins.
3. **Harden atomic saves and audit.** Add concurrent arrival/status/save tests,
   retry behaviour for first-assignment uniqueness races, and an audit-outbox
   failure injection test. The owner-write rollback is verified; transaction
   support requires Mongo replica sets.
4. **Agree data and label semantics.** Missing/null/empty/non-scalar group keys are
   omitted to avoid false duplicates. Numeric and string SBIs remain distinct.
   Counts use active labels plus an explicit excluded count, correcting the
   ticket example's mixed denominator. Confirm withdrawal-request treatment,
   scope departure, historical target wording and whether cycles are permitted.
   Existing cycles are allowed by the supplied rules.
5. **Bound and measure Mongo queries.** Add projections tailored to configuration,
   paging and group-size limits; benchmark realistic group/case volumes and
   completion totals. Detail currently computes all groups then selects by hash.
   No throughput or large-group BSON-limit claim is made by this spike.
6. **Finish frontend behaviour and accessibility.** Refine the external tab
   navigation and final copy, selected-state/error focus and historical label
   wording; browser-test with actual Entra login; verify CSRF/session behaviour
   and responsive/accessibility requirements in the full application.
7. **Production rollout and regression coverage.** Publish the real grant config,
   deploy indexes, define retention of abandoned groups, test broader timeline
   and workflow behaviour, then implement the final change separately from
   these disposable branches. The fixture's status/path names are verified
   against repository code, not the currently published grant release.

Comparison, extra columns, tolerance matching and richer scopes remain outside
the spike. No Jira comments, ticket changes or new tickets have been published.
