# FGP-1594: configurable de-duplication spike

This throwaway change proves configurable grouping in the real backend and
frontend, backed by MongoDB. It is on backend branch `fgp-1594-spike` and frontend
branch `spike/fgp-1594-dedupe`. Both pull requests remain drafts. The purpose is to
inform implementation tickets, rather than make this branch production ready.

## Agreed decisions

- Grouping fields, workflow phase/stage and excluded statuses come from workflow
  configuration. The current definition groups on SBI. There is one dedupe
  definition per case type; `pageKey` identifies navigation, not group identity.
- Assessments are fixed: Not set, Not duplicate and Duplicate with another active
  case. They have no expression DSL. Supporting configured assessments later
  would extend the label policy and presenter, rather than frontend rules.
- Submitted application data, including SBI, is immutable. Workflow position,
  ownership and assessments may change. Missing/null/blank/non-scalar grouping
  values are omitted; numeric and string values remain distinct. A missing SBI
  violates the application input contract and should never reach this feature.
- Duplicate references cannot form direct or indirect cycles, including paths
  through historical references. The spike checks sequential saves. Protecting
  this rule against simultaneous saves is a production follow-up.
- Production grouping configuration becomes immutable once used. Changes require
  an explicit migration. Development/test data can be reset. This spike validates
  configuration structure, but does not implement the production lifecycle guard.

The exact definition is in `test/fixtures/dedupe-page.json`. Its grouping values
are direct paths into immutable submitted data; display fields are direct paths
as well. Workflow validation checks the configured phase, stage and statuses.
It does not prove that an arbitrary grant payload contains the configured field.

## Domain, application and BFF boundaries

`DedupeGroupKey` owns canonical typed identity and its hash. `DedupeGroup` is a
calculated domain read model: it derives active membership, counts, completion,
valid duplicate targets and cycle validation. It does not own the Cases or store
a member list. `GroupAssignment` validates owner eligibility. `Case` records
changed dedupe assessments and their timeline events.

These dedupe domain models contain no HTTP, URLs, form tokens, GOV.UK component
properties or Mongo queries. Existing workflow configuration validation uses the
repository's Joi/Boom convention separately from these rules.

The use case authorises access, loads workflow configuration and eligible users,
coordinates the domain models and repositories, and saves within the existing
transaction/audit boundary. The presenter translates domain results into a BFF
model containing headings, links, summary text, owner and assessment selects,
selected options, disabled states, historical target wording and validation
errors. The presenter also decodes submitted form tokens at the backend boundary.

The frontend renders that model using its Nunjucks/GOV.UK components. It forwards
form values unchanged and renders the backend's validation response. It does not
parse assessment JSON, decide valid targets or completion, invent historical
options, or decide which cases may be assessed. The timeline receives formatted
assessment text from the backend too.

A group BFF row looks like this (illustrative synthetic reference):

```json
{
  "caseLink": { "href": "/cases/0123456789abcdef01234567", "text": "CASE-1" },
  "note": null,
  "labelField": {
    "id": "label-CASE-1",
    "name": "label-CASE-1",
    "label": {
      "text": "Label for case CASE-1",
      "classes": "govuk-visually-hidden"
    },
    "items": [
      { "value": "", "text": "Not set", "selected": true },
      { "value": "NOT_DUPLICATE", "text": "Not duplicate", "selected": false },
      {
        "value": "DUPLICATE:CASE-2",
        "text": "Duplicate with CASE-2",
        "selected": false
      }
    ],
    "disabled": false
  }
}
```

## Mongo storage and live queries

Assessments live on `cases.labels` in the fixed `duplicates` namespace. Changes
append case timeline events. `case_groups` stores only durable group ownership
and identity: `caseType`, `keyHash`, typed `key`, `assignee`, timestamps and an
informational version. It is created on the first owner assignment, not when a
page is read or an assessment alone is saved. Clearing an existing owner keeps
the record. Its unique index is `{caseType: 1, keyHash: 1}`.

The hash is SHA-256 of case type and the canonical typed grouping key. Page names
are absent. Detail URLs carry a reversible base64url encoding of the typed key;
the backend validates its shape against the definition and makes a targeted
scope-and-key query. This avoids recalculating every group to resolve a one-way
hash, and works before any ownership record exists. The key is not secret;
normal role checks protect all reads and writes.

Summary reads scope cases in Mongo, omit invalid keys, project only the fields
needed for dedupe, group by the configured fields, and retain groups with at
least two active members. Excluded cases remain visible inside a group but do
not count towards completion. Owners are fetched in one batch. Counts, members
and completion are recalculated each request; a new unassessed case can reopen
completion without changing ownership. Detail remains readable after membership
drops below two. No full submitted payload is pushed into each Mongo group.

Detail queries use the configured immutable key fields. The supplied migration
adds an index for the SBI definition as well as group ownership. Other grouping
configurations need matching index design. Historical cycle checks currently
load the case type's duplicate-labelled references, which is deliberately simple
for sparse duplicates.

## Verification and local use

Use locked dependencies (`npm ci`), Node 24 and a local Mongo replica set. From
the backend checkout:

```sh
FGP1594_FRONTEND=/path/to/frontend node scripts/verify-dedupe-spike.js
npx vitest run --configLoader native --config test/dedupe.vitest.config.js
```

Both commands create a unique disposable database and remove it afterwards.
They default to `mongodb://127.0.0.1:27017/?directConnection=true`; override
`SPIKE_MONGO_URI` when needed. The cross-app check uses the actual frontend
routes/templates, backend HTTP and Mongo repositories. Authentication is
substituted with a seeded user in that check.

To use the actual applications, configure their usual Mongo, Floci, Entra and
session environment, then seed a new scratch database before starting them:

```sh
MONGO_DATABASE=fgp1594-spike-v2 node --env-file=.env scripts/seed-dedupe-spike.js
MONGO_DATABASE=fgp1594-spike-v2 npm run dev
# In the frontend checkout, point at that backend's configured port:
FG_CW_BACKEND=http://localhost:3201 npm run dev
```

The seed runs migrations first and refuses a non-empty database. Use a fresh DB
for this revision: its hash/index/configuration shape differs from the earlier
spike. Do not reinterpret old assignment data using the new definition. Sign in
as the local Test ReaderWriter user, open `/cases` and choose **Clean the list**.
The seed contains three SBI groups with two active cases each, including one
group with an additional rejected case.

Verified on 16 November 2026: 394 domain/backend regression checks, 10 real
Mongo route/transaction checks, 19 frontend route/use-case/template checks and
the cross-app form/persistence/timeline check. The existing private Tailscale
route was also checked through the actual local stub sign-in. The Mongo suite includes 5,000 mostly
unique additional cases and a few small duplicate groups. A local summary read
was 66–74 ms in local runs; this is feasibility evidence, not a production SLA
or capacity benchmark. The SBI detail query uses an index scan, examines three documents and returns
three members in that dataset. Unrelated payload data is not returned.
The backend lint check uses absolute equivalents of its architecture exception
globs because the existing relative exceptions fail in this hidden `.t3` path.

## Findings to turn into implementation tickets

1. **Production concurrency and safe case writes.** Keep the spike's simple
   last-write-wins behaviour. Production needs a deliberate concurrency design
   covering simultaneous assessments, cycle write skew, arrivals/status changes,
   first-owner races and retry behaviour. Existing ordinary Case saves can
   overwrite labels/timeline read earlier. Namespace revisions must survive
   assessment clears. Check Mongo session propagation in ordinary Case reads.
   An atomic transaction protects this save's writes and audit; it does not
   serialise the business rule across concurrent requests.
2. **Configuration lifecycle and migrations.** Enforce one dedupe definition per
   case type and immutable configuration once used in production. Define the
   registration boundary, workflow version policy across majors and migration
   process for existing labels, identity, owners and indexes. Configuration
   publication should validate immutable payload paths against grant schemas.
3. **Query bounds and operational evidence.** Add paging, group-size limits,
   matching indexes for each definition, bounded historical reference traversal
   and representative load tests. Measure summary totals and sparse/large group
   behaviour separately. Owner names are currently snapshots; choose a live user
   lookup policy and retention policy for old ownership records.
4. **Complete product integration.** Confirm final copy, historical target
   wording, withdrawal-request treatment, error focus, accessibility and
   responsive behaviour. Verify actual Entra/session/CSRF handling and publish
   the real grant configuration. Extend audit failure/retry and rollout coverage.

No locking/guard documents, distributed locks or production migration framework
have been added. No Jira tickets or comments have been published. The deliverable
is working feasibility code and these implementation findings.
